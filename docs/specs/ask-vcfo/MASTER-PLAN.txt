  VCFO Suite · Master plan · 6 November 2026
  Ask VCFO Master Plan
  One chat on top of three engines: Answer, Do and Watch. It joins today's Ask VCFO with the agent idea, adds a knowledge layer, cuts token use, and adds a portal watcher that feeds the chat and the notifications. This is a plan. Nothing has been built or changed. For the simple picture version, see the diagrams, user flows and demo screens.
  Yes, all of this fits one product, and today's Ask VCFO stays as its base. Most questions will not call an AI model at all, because code can answer them exactly and for free.
    Counts come from live data, not RAG
"How many companies are incorporated?" needs an exact count. RAG finds similar text, so it cannot count, and copied data goes stale and can leak across roles. Code counts live records, and RAG handles documents, notes and law.
    The cheapest token is no token
Every step runs the cheapest option that can do the job: code, then a saved answer, then the small model, then the larger model. On my estimate, the same answers use about 87% fewer tokens.
    Some portals refuse automated reading
MCA and Income Tax India returned "Access Denied" to a plain request, and RBI, SEBI and PIB offer working feeds. A blocked source gets a manual or email route. We do not disguise the crawler or solve CAPTCHAs.
  The three engines
The person sees one chat and one notification area. Behind them, each engine has a different job and a different cost.
    Engine | Its job | Who starts it | What it costs in tokens | What protects it | 
      Answer | Explains, counts and finds things, in the same easy cards as today. | A person asks. | None for clicks, recognised questions and saved answers. Small for document answers. | Repository role checks, plus the answer validation you already have. | 
      Do | Fills data into the right field and operates the app. | A person asks for work. | Small for fixed workflows. Large for the open agent loop, so that loop is capped and used rarely. | Review card, tier rules, same rule code as the screens. | 
      Watch | Checks official portals, summarises what changed and publishes it. | A schedule, with no chat involved. | None when nothing changed. One small model call per genuinely new item. | Model has no tools, code checks its summary against the source, and a person reviews before clients see it. |

  The recommended shape
Questions keep the fast, cheap path you already have, with cheaper steps added in front of it. Work goes through a path that ends at a person's approval. Watch runs on its own schedule and meets the others at the knowledge layer and the notifications.
    The signed-in personTypes, pastes a table or drops files, from any page
    ↓
    Chat surface ExtendPanel and full page, plus uploads, current page and record, and review cards
    ↓
      Free checks ExtendSuggestion click, local match on metrics and reviewed topics, saved answer. No model.
      Router ExtendToday's guard on Haiku 5.5. It sorts what the free checks could not.
    ↓ question, or work to do
      Answer engine ExtendMetric catalog for exact facts, hybrid search for text, small model to write it up
      Do: fixed workflows NewData router and common actions, in short model steps with code around them
      Do: agent run NewOne capped model loop in an Inngest job, only for open-ended work. It can wait for an approval and then resume.
    ↓ uses
      Knowledge layer ExtendLive facts, record cards, documents and regulatory updates, each with a date and a source
      Field catalog NewEvery place a value can go, generated from your own field definitions
      Action registry NewOne definition per action: input, risk tier, roles, preview, execute, undo
    ↓ proposes, never writes
    Changeset and approval gate NewOld value, new value, source, check result. Code checks it again at the click, and the approval is tied to that exact content.
    ↓ after approval
      Shared rule code, then repositories ExistsSame AuthContext, validators, notifications and audit events as the screens. Postgres and S3 stay as they are.
      VCFO Assist, then MCA portal On holdNeeds written CS approval. The extension fills, and a person logs in, signs, pays and submits.
    Separately, on a schedule and with no chat involved
      Watch engine NewOfficial portals, change check, noise filter, small model summary, code check of that summary, manager review
      Announcements and bell ExistsApp code posts to the board, popup and notification tab. The chat does not send these.
      Knowledge layer ExtendThe same update is indexed, so the chat can answer about it with its source
    Across all layers
    Evals, traces, cost limits, kill switch ExtendEvery run is recorded and can be replayed. Token use is reported per path. No new action ships without tests.

  The knowledge layer: your RAG, done properly
You asked for a RAG that stores all the data and answers anything. The experience you describe is right, and it takes four stores behind one question box, because different questions need different methods. The person never has to choose.
    Store | Status | What it holds | Example question | How it answers | Tokens | 
      Live facts | Exists | Companies, steps, filings, tasks, invoices, people. They stay in their own tables and are never copied. | "How many companies are incorporated this year?" | A named metric calls a repository with the person's access, and a template writes the sentence. | None, or about 860 for the router | 
      Record cards | New | A short text card per record, built from notes, comments, requests and task titles. Identity numbers are left out. | "Which client had the landlord NOC problem?" | Hybrid search, limited first to records this person may see. | About 3,250 to write the answer, plus the router | 
      Documents | Extend | Reviewed topics, firm playbook, obligation texts, statutory calendar, acts and rules, firm procedures. | "What is the penalty for a late AOC-4?" | A reviewed topic if one exists.   The token plan
The ladder below decides how each message is handled, and it stops at the first step that can answer. Today's numbers come from your 30 September live eval, which used fixture data. All other figures are my estimates, and phase 0 replaces them with real production usage.
    Step | Status | What handles it | Tokens per message | Estimated cost | Estimated share of messages | 
      1. Suggestion click | Exists | Code, as today | 0 | $0 | 30% | 
      2. Recognised question | New | Code matches a metric or reviewed topic and skips the guard | 0 | $0 | 35% together | 
      3. Saved answer | New | Same wording, audience and knowledge version as an earlier document answer | 0 | $0 | 
      4. Router, then a fact | Extend | Haiku 5.5 picks a metric from a short list, and code does the rest | About 860 | About $0.0001 | 10% | 
      5. Document answer | Extend | Router, 4 sources, one short answer. Test Haiku 5.5 first and use Sonnet 5.5 if evals need it. | About 4,100 | $0.0005 to $0.009 | 20% | 
      6. Fixed workflow | New | Short model steps with code around them, such as filing data into fields | About 6,900 | $0.001 to $0.02 | 4% | 
      7. Agent loop | New | Sonnet 5.5 with a capped budget, only for open-ended work | About 126,000 | About $0.13 | 1% | 
    At 2,200 messages a month | Tokens a month | Cost a month | Can it do the work? | 
      Today's Ask VCFO | About 16 million | About $25 | Answers only, and no firm counts | 
      This plan, including Watch | About 6.4 million | About $3 to $9 | Answers, counts, filing data, actions and portal updates | 
      Sending all typed messages through an agent | About 194 million | About $200 | The same, at many times the price | 
  The volume of about 100 messages per working day is an assumption. The agent loop accounts for about 43% of the plan's tokens at only 1% of messages, so keeping it rare and capped matters more than any other setting. Answers alone fall from about 16 million tokens to about 2.1 million, which is the 87% reduction quoted above. Cache writes are not logged today, so the current figure is slightly low.

      Move the guard to Haiku 5.5 | One setting, plus disabling thinking for this call. | Listed at a tenth of the Haiku 4.5 price. | Rerun the 29 live eval cases first. | 
      Local match first | Aliases for metrics, topics and greetings, checked in code before any call. | A recognised message costs nothing. | A wrong match gives a wrong answer, so match strictly and let the rest fall through. |

  The Watch engine: portal updates
You called this an agent. I recommend building it as a fixed pipeline with one small model step, because a free-roaming agent reading hostile web pages would cost more and carry more risk for no better result.
    Step | What happens | Done by | Tokens | What stops a mistake | 
      1. Check | Feeds every 3 hours and pages twice a day. Uses conditional requests and a content hash, and stops here if nothing changed. | Code | 0 | Reuses your host allowlist and safe-URL checks. It only reads public pages and never logs in. | 
      2. Find new items | A small adapter per source lists title, date and link. New ones are matched against what is stored. | Code | 0 | An adapter returning nothing raises an alert, in case the page layout changed. | 
      3. Drop noise | Source rules remove tenders, jobs and routine auctions. | Code | 0 | Dropped items are kept in a log, so the rules can be audited. | 
      4. Read | Download the PDF or page and extract the text. | Code | 0 for text | A size limit applies. Scanned PDFs alone go to the model. | 
      5. Understand | Returns area, act, change type, effective date, any new due date, who it affects, a plain summary and an exact quote. | Haiku 5.5 | About 2,300 | Strict schema and no tools at all, so a hostile page has nothing to trigger. Page text is treated as data. | 
      6. Verify | Every date and number in the summary must appear in the source, and the quote must match exactly. | Code | 0 | A failed check marks the item for extra attention and does not send it out. | 
      7. Merge | The same circular from two sources becomes one update, keeping both links. | Code | 0 | Unsure matches stay separate. A person can merge them later. | 
      8. Review | Staff see it at once, marked "Not yet reviewed". A manager edits or publishes with one click. | Person | 0 | Nothing reaches clients unreviewed, because a wrong due date from the firm would cost trust. | 
      9. Publish | Adds it to the board and popup, the notification tab and the chat knowledge together. | Code | 0 | Code picks recipients using fixed rules. Neither the chat nor the model chooses them. | 
      10. Follow up (later) | A due-date change becomes a proposal to update the calendar, and leads see which of their clients are affected. | Code, person | 0 | The calendar is never changed automatically. A manager approves it. |

    Rule | What it means | 
      A blocked source stays blocked | The crawler uses its real name, respects robots rules and rate limits, and never solves a CAPTCHA, rotates identity or logs in. Getting around a block on a government site brings legal risk to a compliance firm. | 
      Manual intake is first-class | Staff paste a link or upload a PDF, and it enters the same pipeline at step 4. MCA needs this from day one, because it is your most important source. | 
      Official alert emails as a second route | Where a department offers an email alert, a firm mailbox can feed the pipeline. I have not confirmed which ones do. | 
      Silence must not look like "no news" | Each source shows its last successful check, using your service-checks job. The chat says "no updates found from these sources as of this date", and it never says that the law has not changed. | 
      Official sources only | Paid or commentary sites are not scraped. Their content has its own licence, and the firm should rely on the original notification. | 
      Short summary and a link | The update keeps a short quote and a link to the original, and the original remains the authority. |

  Running cost, as an estimate to replace with real numbers: an agent run of 6 model turns, 120,000 input tokens at 80% cache hits and 6,000 output tokens costs about $0.13 on Sonnet 5.5 or $0.24 on Opus 5.5, before cache-write charges.   Worked example: "How many companies are incorporated this year?"
This one should cost nothing, and it still answers in the same easy card as today.
    Step | What happens | Done by | What stops a mistake | 
      1. Recognise | Code matches "how many", "companies" and "incorporated" to the metric companies.incorporated, with the period set to this financial year. | Code | Only a strict match skips the model. Anything less clear goes to the router, which may choose only from the metric list. | 
      2. Count | A repository counts the engagements with an incorporation date in that period, using the person's AuthContext. | Code | An admin gets the firm's number, a lead gets their own, and a client gets only their own company. | 
      3. Say it simply | A template fills in the existing answer card: "7 companies since 1 April", a small chart by month, and a link to the list. | Code | The number comes from the count, so a model cannot get it wrong. | 
      4. Follow-up | "Why is Cedar still pending?" is a different kind of question, so it uses project tools and a short model answer. | Model | Your existing answer validation checks dates, steps and citations. |

  Worked example: "Add this as director 2 for Acme"
The person drops a PAN card and an Aadhaar card into the chat. Code does as much as possible, because code cannot invent a value.
    Step | What happens | Done by | What stops a mistake | 
      1. Take in | Files go to S3 through the normal upload path. The run is locked to the person and to Acme's engagement. | Code | A repository call confirms this person can reach Acme. If two companies match, the agent asks. | 
      2. Read | The model identifies the document type and extracts name, PAN and date of birth, each with its page reference. | Model | A strict schema. Any instruction printed inside the document is treated as data. | 
      3. Check format | The PAN pattern and the date are checked. | Code | A failed check goes to the person as a question, and no guess is made. | 
      4. Find the place | The catalog returns candidates, such as director.pan in the pre-15 entry. The model chooses from that list only. | Code, then model | The model cannot name a field that the catalog did not offer. | 
      5. Check the rules | The existing checks run: step gate, who may fill the field, conditions, step validators. | Code | A locked step is held and labelled. A field this role cannot edit is routed to the right person. | 
      6. Find conflicts | The value is compared with what is saved, and with other steps that hold the same fact. | Code | An existing value is never silently overwritten. The difference is shown. | 
      7. Show the review | A card lists step, field, old value, new value, source page and check result, with Accept or Edit on every row. | Person | Nothing has been saved up to this point. | 
      8. Save | On the click, code checks everything again and calls the same rule code as the screen. Audit and notifications run as usual. | Code | The approval only matches this exact content. The person can undo from the card. |

  What I would not build
Each of these sounds advanced but would make this system worse at this stage.
    Idea | Why not | Use instead | 
      Model writes SQL against Postgres | It bypasses the seam and role scoping, which are your strongest protections. | Typed read tools over repositories | 
      Agent clicks through your own website | Slow and fragile, and you own the code, so there is no reason to go through the screen. | Direct actions, and on-screen highlights only to show the result | 
      One tool generated per API route | Routes were written for screens, so inputs are hard for a model to use and risk levels are unknown. | Hand-reviewed actions, added in priority order | 
      Agent with its own powerful account | Anyone chatting could reach data beyond their role, as Notion's help page warns. | Every run uses the person's AuthContext | 
      A swarm of many agents | More cost and more places to fail. Mapping is mostly a fixed workflow. | One loop plus fixed workflows; a second-model check for high-risk items only | 
      Knowledge graph or a separate vector database now | Your document volume is small. Sources I read say to prove plain retrieval is the bottleneck first, and report that pgvector scales into the millions. | pgvector in the same Postgres | 
      Rewriting the app first | The foundation works, and your rules ask that ported domain code stays as it is. | Move routes to shared actions one at a time | 
      Copying all data into RAG | A vector search cannot count, copies go stale, and a shared index can leak across clients. | Live facts through metrics, and an index only for free text | 
      Matching saved answers by similar meaning | "GSTR-1 due date" and "GSTR-3B due date" look nearly the same to a vector, and returning the wrong one would be serious. | Exact match on normalised wording | 
      The model reading every portal page | This burns tokens on pages that have not changed, and it exposes the model to hostile content for no gain. | Hash check and adapters in code, with the model only on new items | 
      A free-roaming scraping agent | It costs more and is harder to test. A page could also instruct an agent that holds tools. | A fixed pipeline, where the model step has no tools | 
      Disguising the crawler to get past blocks | It carries legal risk for a compliance firm, and it would break whenever the site tightens its rules. | Manual intake, official emails and the sources that allow reading | 
      Letting the model choose who gets notified | A wrong guess means a person misses a deadline change. | Fixed recipient rules in code | 
      Auto-editing the compliance calendar | One misread date would change deadlines for every client. | A proposal that a manager approves | 
  Build order
This replaces my earlier order. Token fixes come first because they pay back immediately, and facts and Watch come early because they ship quickly and every role sees them. Each phase is useful alone. Weeks assume one developer working with AI, and they are estimates. Nothing starts until you say go.
    Phase | Weeks | Engine | What gets built | Done when | 
      0. Measure and cut | 1 | Answer | Read real usage from production ask_messages, log cache writes and path, move the guard to Haiku 5.5, trim history, sources and table rows, and add a token report. | The 29 live eval cases still pass, and tokens per answer are measurably lower. | 
      1. Facts | 2 to 3 | Answer | Metric catalog of about 25 metrics, local match, answer templates, and access for managers and leads if you approve. | Your incorporation question gets an exact, role-correct answer with no model call. | 
      2. Knowledge | 4 to 5 | Answer | pgvector, embeddings, rank fusion, local PDF text, record cards, dated sources, saved answers, and loading the real documents. | Paraphrased and Hinglish questions pass the eval, with correct citations and no cross-client result. | 
      3. Watch, first release | 6 to 7 | Watch | Source registry, health display, feeds and working pages, manual intake, summary and code check, manager review, publish to board, bell and chat. | A real week of updates is reviewed with no wrong date, and a broken source raises an alert. | 
      4. Paste and file | 8 to 10 | Do | Field catalog, data router, changeset card and undo, for incorporation steps only. | A lead drops real documents and reviews correct proposals. Suggested target: 98% correct fields on proposed rows, and no wrong-client write. |

      6. Watch, second release | 14 to 15 | Watch | Affected-client lists, calendar change proposals, official alert mailbox, and remaining sources. | A due-date change produces a correct proposal and client list, approved by a manager. |

  Decisions that are yours
These change the design, and my recommendation is given for each.
    Decision | Why it matters | My recommendation | 
      Build order | I moved token fixes, facts and Watch ahead of filing SPICe+ from chat. If filing is your top priority, it can go straight after phase 0. | Keep the order above. Filing needs the most testing, and the earlier phases give value sooner. | 
      Open chat to managers and leads? | The current spec blocks both roles, while "use the whole website" needs them. | Yes, in phase 1, starting with read-only questions. | 
      Who reviews Watch updates? | Review is the safety gate, and a queue nobody owns will stall every update. | Name one manager and one backup. Set a same-day target for Important items. | 
      Notify clients of every update? | You said everyone. Clients may get many items that do not apply to them, and may start to ignore them. | Follow your rule at launch, as in the table above. Once client matching exists, consider sending clients only what applies to them. | 
      Allow scraping of public pages? | Your notes say HTML pages are not scraped, so this is a rule change. Government sites also have their own terms. | Allow public listing pages from official hosts, after reading each site's terms. Ask counsel for a short view, along with the CS opinion. | 
      How to cover MCA? | It is your most important source, and it refused plain requests in my test. | Start with manual intake and official emails, retest from AWS Mumbai, and do not attempt to get around a block. | 
      Who uses the Do engine first? | Clients and staff carry very different risk. | Project leads first, since they already review this data. Clients come after phase 5. | 
      May the model read identity documents? | Today's rule is that Ask tools never see identity numbers, but filling from a PAN card needs this. | Allow it for extraction only, and mask those values in chat, logs and stored prompts.       Anthropic API or Amazon Bedrock? | This affects where client data is processed. The code already supports both, though features differ slightly. | Keep the current API for the test-data phase, and decide together with the question above before real data. | 
      Stay on App Runner? | AWS closed App Runner to new customers in April 2026. Existing services continue, with no new features planned. | No move for this project. Agent runs in Inngest do not depend on long web requests, but test streaming limits early and plan a separate review of hosting. | 
      The CS opinion | The portal hand-off cannot start without it, while phases 0 to 7 do not need it. | Keep it moving in parallel. Do not make the agent wait for it. |
